## 1. BUG CRITIQUE — claim AUTO échoué (src/real.ts)

**Symptôme (17:15)** : `TypeError: Cannot read properties of undefined (reading 'toBuffer')`
au claim AUTO — fees 25.10$ restées on-chain, retentative à chaque cycle.

**Cause racine** : le SDK `claimAllRewardsByPosition` destructure `{owner, position}`.
Le code passait `user` (comme les autres méthodes) → `owner` undefined →
`compileToV0Message` appelle `payer.toBuffer()` sur undefined (simulation CU).

**Fix** : `claimAllRewardsByPosition({ owner: user.publicKey, position: pos })`.
⚠️ `removeLiquidity` (shouldClaimAndClose) appelle AUSSI claim en interne — le
même bug aurait cassé les auto-closes.

**Validation** : tsc 0 erreur, dry-run (construction tx, feePayer = wallet),
test réel via le chemin exact du cron (XST-SOL auto-clos par recovery-exit au
même cycle — claim absorbé par le close, sig 641vEQn3…).

## 8. ws-pool-monitor — TEMPS RÉEL <1s (scripts/ws-pool-monitor.ts, nouveau)

Étape 3 anti-limite-API : le polling Data API (fenêtre volume min = 5 min)
est contourné par un websocket Helius (clé API déjà en place) :
- **3 abonnements par position ouverte** : le compte LbPair (active_id/
  bin_step → prix) + les 2 comptes token reserve_x/reserve_y (amount u64 @
  offset 64) → chaque swap les modifie → **les deltas SONT le volume temps
  réel**, zéro polling.
- Table `pool_events_rt` (rétention 24h), heartbeat /tmp, reconnexion
  backoff (1→30s), refresh des positions toutes les 5 min, arrêt propre.
- Durabilité : wrapper dlmm-wsmonitor.sh + @reboot + garde du watchdog.
- **Pièges SDK attrapés** : le type IDL s'appelle « lbPair » (minuscule),
  champs snake_case ; `reserve_x/reserve_y` sont des PUBKEYS (comptes token),
  PAS les montants ; pools meme-SOL : la réserve wSOL garde un buffer
  constant (wrap/unwrap immédiat) → ΔY ≈ 0, le signal de volume est le côté
  TOKEN (ΔX).
- Mesuré : MANLET 227k tokens en 90s pendant une descente dans l'échelle.
